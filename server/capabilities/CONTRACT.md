# Base 插件合同与验证

本应用使用 `@official-plugins/feishu-bitable@1.0.22`。五个实例来自现有 Base 真实表结构；插件输入由 `CrmService` 固定操作白名单生成，不接受前端传入表ID或action。

| action | 关键输入 | 响应 |
| --- | --- | --- |
| searchRecords | pageSize、pageToken、filter | records、hasMore、pageToken |
| getRecord | recordID | id、record |
| batchAddRecords | records: [{record}] | records: [{id}] |
| batchUpdateRecords | records: [{id,record}] | records: [{id}] |
| aggregateQuery | measures: [{fieldName,aggregation:'count',alias:'total'}] | result: [{total:{value}}] |

文本读取为 `{text}`、写入字符串；人员为妙搭数值ID数组，转换时必须拒绝不安全整数。关联读取为 `{link_record_ids}`，写入必须是记录ID字符串数组；不能把读取形状原样写回。日期为毫秒时间戳，界面日期按 Asia/Shanghai 解释。可选字段接受省略但当前插件不接受 null，因此不能用 null 清日期；终局确认等需要清空日期的业务动作保留原生入口。

合同来自实际安装包 schema projection 和真实 SDK 读写验证：2026-10-24 客户→联系人→项目→跟进创建、回读、核查、计划和结束建议均通过，4条临时记录已反向清理。该联调验证SDK/业务服务，不等同于线上浏览器登录验收。

权限：插件按应用所有者 Base 权限运行；发布可见范围为 Tenant，平台限制为本企业已登录成员，业务不要求单独分配员工角色。`crm_admin` 来自可信请求上下文，仅用于限制权限配置；意向字段不授予角色。没有向员工开放删除接口。原始 capability/debug 控制器全局拒绝，避免绕过字段和关系校验。请求、响应正文日志关闭；HTTP错误不暴露内部堆栈。

## 生命周期扩展（2026-10-24）

Schema摘录：`crm-project` / `crm-customer`，`getRecord`、`searchRecords`、`batchUpdateRecords`，均为 unary。更新输入要求 records:[{id,record}]，输出 records:[{id}]；DateTime 为 number，SingleSelect/Text 为 string，User 为 number[]。动态投影见父目录 verification/miaoda-preflight/lifecycle-plugin-projection.json。按受保护的服务端流程调用，保持官方插件包和实例字段类型不变。

新增 `confirm-end`、`archive`、`restore`、`reopen` 四种业务操作，字段由服务端白名单生成。完成/取消日期不得早于已有正常跟进及本轮重开日；客户归档逐个核对关联项目并要求归档阻塞数明确为0；重开须父客户未归档并已核查。受影响父/子记录在写前逐个再读，目标记录仍执行版本及完整快照检查。

已真实验证 SingleSelect 空字符串可清空已处理的结束建议。DateTime 不能提交 null，生命周期操作保留上次结束/归档时间作历史，当前效力按终局及归档标志判断；重开必须新计划。管理记录追加 CRM_LIFECYCLE_V1 JSON快照，历史补录拒绝已记录的非活动区间。历史字段与日志不提供跨实例原子事务或不可篡改审计保证。

更新开始检查客户端修改时间；人员/关系校验结束后，再读取目标记录并比较完整字段快照，同实例同记录更新互斥。但 Base 不提供原子CAS：最终检查到写入之间、跨实例以及关联记录自身仍存在竞争窗口。所有新建/更新均核对写入返回ID并逐字段回读，回读失败或不一致不报告成功。写请求无自动重试；网络超时或服务端5xx会锁定当前表单重提，提示先刷新核对。当前没有持久幂等键，不能承诺跨标签页重复提交恰好执行一次。

权限意向表的可选文本字段：明确提交空值写为空字符串，省略则保留。联系人/项目的所属企业必须唯一；历史停用联系人仅在状态为“停用”、停用时间有限且实际发生时间严格早于停用时间时接受，未知状态拒绝。校验核查记录时保留原始毫秒时间精度。业务服务日志仅记录插件操作名称，不打印上游错误原文。

## 日常编辑

`PATCH /api/crm/records/:kind/:id/edit` 接受 `{changes,reason,expectedModifiedAt}`，白名单来自shared/crm-edit。服务端读取当前记录后合并变更、重新校验必填/人员/关系/业务规则，仅更新变化字段并重置待核查、追加修改说明。保存后按字段回读比对，任何不一致均提示刷新核对；不自动重试。

所属企业、跟进归属及客户/项目关联不允许通过日常编辑修改，当前计划使用已有独立操作。终局、归档、记录状态和核查标记不接收客户端修改。已归档/结束/停用/作废记录不提供日常编辑。空文本写空字符串、空人员/联系人关联写数组；日期、数值、单选清空在调用插件前拒绝，避免假成功或保留旧值。

## 流程修复

`PATCH /api/crm/records/project/:id/progress` 按 shared/api.interface.ts 的 CrmProgressRequest 合同维护工作状态、当前进展、暂停原因及恢复计划。暂停不改旧计划；非暂停必须确认行动和日期，暂停原因写空文本；管理记录追加，核查标记转待核查。与计划/结束建议操作一样校验唯一、已核查且未归档的所属企业，终局或已归档项目不能继续推进。暂停项目核查要求原因，不强求计划；进行中核查必须有当前进展。

跟进的生命周期准入使用实际发生时间。结束日期是北京时间日期（含当天），归档及停用是严格时间边界；缺失边界或非法终局拒绝并提示原表核对。不会因父对象归档而一律拒绝历史补录。核查历史跟进时要求人员存在于同步目录，允许其当前未激活；普通内容编辑中未改变的历史人员不重新要求激活，新选人员仍校验当前激活状态。这些是事实校验，不授予人员运行时权限。

## 交叉规则统一

`existingProjectFields` 统一已有项目编辑/核查的计划要求，暂停及合法终局不强制活动计划，新建仍须填写。`projectReviewProblem` 供页面和服务端共同识别非法状态、非终局归档、缺进展/暂停原因、缺结束信息、未来日期及归档信息不完整；日常编辑也拒绝非法终局。

根据详细设计3.3，非销售项目可保留历史商务字段供核查。类型切换只写类型与审计说明，不写回或清空原金额；服务端仅允许原商务值保持一致，禁止在非销售项目上新增或修改商务信息。新建非销售项目仍不接受这些字段。现有总数统计未新增金额图表，不能将保留的历史值纳入非销售商务金额。

## 全对象核查与公式值

SDK公式/lookup结果可能为 `{bizType,value:[scalar]}`，共享textValue解析数组，保留0与布尔值。页面和服务端共用recordReviewProblem：现有“数据检查”非空时阻止核查，基础管理状态不依赖延迟公式；归档客户要求阻塞项目数明确为0，空值/异常值不能当作0。公式重算期间提示刷新，不自动重试写入，也不承诺关联表原子快照。

联系人停用时间必须有限且不晚于当前时间，原因必须完整；有效身份不得残留停用信息。跟进必须为正常或带原因的已作废状态，核查不会解除作废。未归档客户计划可整体为空，但已有任一计划字段时须行动/日期完整；已归档客户不强求历史计划完整，与Base缺计划公式一致。非法非终局工作状态不能普通编辑或新增历史跟进，可通过进展操作纠正。

终局项目复核不要求父客户处于“正常且未归档”，避免客户归档就绪聚合与项目核查形成循环；仍检查企业关联唯一及存在，客户已归档时校验结束日期不晚于归档所在北京时间日期。创建与非终局业务保持原限制。历史跟进变更多人数组时逐ID检查新增成员激活，已有历史成员可保留；核查仍要求目录存在。


## 项目驾驶舱与筛选

GET /api/crm/overview?scope=all|mine 经可信员工/管理员会话验证后，从项目全部分页构建指标与最多8条项目跟踪；mine仅按请求用户的项目负责人ID匹配，不接受客户端指定他人身份。

GET /api/crm/records/project?scope=all|mine&projectFilter=... 提供同口径筛选与标题搜索，含全部未归档、在办、关注、本月完成、三类风险、五种状态和归档。其他数据类型拒绝项目筛选。原未传此筛选的记录选择器保持原SDK分页行为。

项目数据按当前终局/工作状态分类，不依赖可能延迟的通用状态公式。统计读取至分页结束，拒绝缺失/重复令牌、重复记录及超过100页；不把首50条当作总数。风险为逾期、缺计划、资料待核查/异常的项目去重并集；暂停不按逾期催办。日期按北京时间日/月计算，历史结束日期只在当前终局完成时参与本月完成，已归档排除。

列表按风险和临近截止优先，再按修改时间与ID稳定排序。每次请求重新读取，未提供跨请求固定快照或大型数据集仓库；大量项目需后续改为聚合/物化指标。数据重算或跨页并发仍遵循现有Base一致性边界。

## 客户全览（2026-10-26）

新增受现有员工/管理员会话保护的只读接口：`GET /api/crm/customers/:id/projects`、`GET /api/crm/customers/:id/followups`、`GET /api/crm/projects/:id/followups`。复用五个现有 Base 插件实例，不新增数据表或授权来源。

客户全部跟进包含直接客户关系匹配的记录及该客户全部项目的跟进，按记录ID去重；项目归属从项目表的所属企业字段查询，不依赖可能延迟的客户反向关联。保留待核查、作废、已结束及归档历史。客户支持 all/direct/project 范围及主题、结论搜索，时间线按实际发生时间倒序。联系人仍通过现有 customers/:id/contacts 精确关联查询。

关联查询遍历匹配记录的全部 Base 分页，关系 OR 条件分组为每组30项；单次请求最多100次 searchRecords 调用，超限、重复记录/令牌及异常归属明确失败，不返回首批近似总数。前端每页30条，续页签名绑定父对象、筛选及结果ID/修改时间；数据变化时要求重新加载。重新查询不提供 Base 跨表原子快照。

客户详情默认显示全部跟进，可切换联系人、关联项目、资料；项目详情提供项目跟进及客户联系人，子详情保留返回客户全览入口。顶部保留主要操作，计划、进展及生命周期入口收进更多操作，准入规则沿用共享业务校验。

## 企业全员访问与配置简化（2026-10-26）

本节替代上文旧版的员工角色门槛与目录激活校验。平台运行时可见范围必须为 Tenant 且要求登录；Controller 保留 NeedLogin，可信 userContext.userId 存在即可使用业务接口。角色缺失与空数组均不阻止业务访问；格式异常拒绝请求。权限配置仍要求平台真实 crm_admin，前端隐藏管理员入口不能替代服务端校验。

待配置角色仅有“员工、管理员”，仍为意向字段；删除目录状态与处理请求，移除待处理授权、待目录核验视图，管理授权名单更名管理员名单。插件映射与可写白名单同步删除旧字段，旧请求继续提交旧字段会被拒绝。

业务人员使用 AuthNPaasService.getBatchLarkUserIds / getBatchMiaodaUserIds 校验，最多每批100个，输入输出等长同序；通过应用上下文中的企业员工ID双向转换并核对原妙搭ID，不依赖预先同步名单。失败不绕过、不打印上游错误；未知/不匹配身份拒绝。历史跟进核查可保留原已同步且不再有平台映射的企业成员；新增人员仍须实时校验。未改动历史参与者的普通编辑继续保留原事实。

本次不新增或扩大管理员角色成员，也不提供删除业务接口。企业边界由发布平台 Tenant 可见范围落实，禁止将发布可见范围改为互联网公开。迁移先备份字段、人员记录及视图配置，在兼容代码发布成功后执行并回读。

## 自动跟进状态替代核查流程（2026-10-26）

本节替代上文所有人工核查准入规则。四类业务不再读取或写入核查标记，不提供核查操作；新增、编辑、关联、历史跟进、结束确认及归档不依赖人工核查。必填、企业身份、关联归属、时间边界、并发保护和保存回读继续生效。修改日志写入管理记录（联系人使用联系人管理记录）；原核查字段与记录先完整备份，退出插件投影及界面，在旧Base中隐藏保留。

客户和项目跟进状态只按北京时间的自然日及下次跟进日期计算：至少两天后为等待中，明天为明日跟进（黄色），当天为今日跟进（红色），过期为已逾期N天（深红色），空日期为未安排；客户归档、项目结束或归档优先显示无需跟进。暂停项目有计划日期时仍按日期提醒。记录沟通不自动覆盖当前计划或解除提醒。前端定时及恢复焦点时重算状态，日期跨天重新读取列表和概览。

客户与项目列表支持跟进状态筛选，服务端遍历完整分页后筛选排序，不对首批数据作全局推断；顺序为逾期（越久越靠前）、今天、明天、未安排、等待中、无需跟进。项目原有范围和状态筛选与跟进状态条件取交集。Base质量及有效统计保留自动数据检查，移除人工核查依赖；联系人及跟进记录不新增重复提醒。

## 详情业务化展示（2026-10-27）

详情页按业务字段白名单分组，不再兜底展示其他系统字段；允许员工维护、质量正常、存在当前计划、长期未跟进及归档阻塞项目数不独立展示。业务概况显示在办项目（个）、未跟进时长（天），长期未跟进采用原公式值显示黄色标签。操作信息包含创建人、创建时间、最近修改人、最近修改时间，默认折叠；空字段隐藏，保留有效的0和false。

布尔值兼容原生值、公式字符串和包装值，归档状态显示已归档/未归档，不把缺失值推断为否；数量显示单位。客户归档操作遇到有阻塞项目时给出数量提示和查看项目入口；后端原有归档校验继续生效。上述变更仅影响展示，不删除底层字段或变更业务权限及计算口径。
# 清理停用字段（2026-10-27）

四张业务表删除停用的核查标记和核查说明；历史说明先转存管理记录，原结构和记录留有迁移备份。客户、项目删除没有发送服务使用的最近成功提醒键/时间及旧原生权限规则的允许员工维护公式。应用数据源、建表定义和部署蓝图同步移除，避免查询已删除字段或在新企业重新创建。跟进状态、自动数据检查、统计公式、业务负责人、终局、归档及时间边界继续保留。
