# 跟进记录的连续推进

## 使用方式

- 一个项目可有多条独立跟进，各自设置下一步建议、建议执行人和建议日期。
- 在待跟进记录或工作台点击「继续跟进」，填写本次结果。保存后，原记录显示「已跟进」，新记录按自己的后续安排继续提醒。
- 从菜单独立新建时，「接着哪次跟进」可选；不选就建立独立跟进。只允许关联同一个客户直接跟进，或同一个项目的待跟进记录。
- 「结束跟进」停止该条安排的提醒，可填写说明，不删除或改写原有建议、日期和附件。
- 历史记录不会自动成为待办；需要继续的历史建议可在详情中选择「纳入待跟进」。
- 项目列表汇总待跟进数量、逾期数量、最早建议日期。时间筛选匹配任意一条待跟进，不只匹配最早日期。
- 工作台「我的」待办按建议执行人筛选。每日通知沿用原时间与成员配置，仅向已启用成员发送其本人今日、明日的待跟进；未指定执行人仍在全员工作台显示，不群发。

## 数据与一致性

在现有跟进记录表增量增加：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| 上次跟进 | 单向关联本表 | 新记录指向上一条记录，创建后不可从编辑表单更改 |
| 后续处理 | 单选：待跟进、已结束 | 是否启用待办或明确结束；空值代表上线前历史记录 |
| 结束跟进说明 | 文本 | 主动结束说明 |

应用显示的「已跟进」由正常后续记录反向推导，不把它作为第二次跨记录写入。前后关联与新跟进内容在同一次新增中保存，因此没有“新记录成功、旧状态更新失败”的半完成步骤。项目、客户旧计划字段和历史记录均保留，但不再作为当前工作台和通知的数据源。

服务端检查同一业务对象、时间顺序、待跟进状态和编辑版本；同进程重叠操作由原记录锁互斥。Base 不提供原子条件新增，多实例恰好同时提交仍可能产生多个合法后续分支；系统保留并展示全部关联，不覆盖任一记录。网络结果未知时不自动重试新增。

作废的后续记录不再代表一次有效处理；其上一条会重新成为待跟进。已存在后续记录时，修改时间不能破坏前后顺序。修改历史记录不会自动将其纳入待办。

## 部署

正式应用只增字段，不清空、不迁移业务记录。新增字段定义见 `scripts/followup-chain-fields.json`；其他企业部署时，关联的 `link_table` 必须替换为目标企业的跟进记录表 ID，并将返回的字段 ID 写入 `server/capabilities/crm-followup.json`。不要在同一表重复创建字段。

仓库外的 `../scripts/schema.mjs`、`../deploy/blueprint.json` 已同步此增量结构，供后续独立企业部署使用。本次未重打旧部署压缩包；使用旧压缩包前需同步新版源码与结构。

回滚应用代码不会删除新增字段或业务记录；再次启用本版本时仍可读取已保存的关联。

## 验证

`npm test` 包括多人并行、前后关联单次写入、重复继续拦截、结束保留历史与附件、历史显式启用、跨项目/倒序时间拒绝、分页与筛选、个人通知和前端继续跟进入口回归。测试使用隔离数据，不向正式业务表写入验证记录。
